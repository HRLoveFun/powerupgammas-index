# PowerUpGammas 视频索引

一个单文件的视频索引页：按时间浏览全部公开视频、按标签筛选、查看视频之间的引用关系并连线。

交付物是 **`index.html`**（自包含，双击即可在浏览器打开，无需服务器）。

---

## 一、数据源核实结论

在动手前对频道做了实测（2026-11），结果决定了后面的方案：

| 数据源 | 可达性 | 实测结论 |
|---|---|---|
| `/videos` 标签页 | ✅ 可用 | `yt-dlp --flat-playlist` 拿到全部 **380** 个视频的 ID 与标题；但**不含发布日期** |
| `/playlists` 标签页 | ✅ 可用 | **15 个播放列表**，覆盖 291 个视频（76%），是唯一可靠的现成分类体系 |
| 单个视频页（默认 UA） | ❌ 被拦 | 返回 `Sign in to confirm you're not a bot`，所有 player client（tv / mweb / ios / android_vr…）均被拦 |
| 单个视频页（爬虫 UA） | ✅ 可用 | 用 `facebookexternalhit / Googlebot` 取到 HTML，内含 `ytInitialPlayerResponse`：精确 `uploadDate`、完整简介、时长。**380/380 全部拿到日期** |
| 字幕 / 文字稿 | ❌ 不可用 | 该路径下 `captions` 为空且 `playabilityStatus: UNPLAYABLE`；`timedtext` 与 `get_transcript` 均因签名/风控返回空或 400 |
| 简介中的频道内链接 | ⚠️ 需清洗 | 表面有 1356 条链接，但 **164/380** 篇简介共用同一段「✳️ 其他期权视频」模板，逐条照收会得到一张假关系网 |

### 由此得到的两个关键判断

**1. 标签：播放列表最可靠。**
15 个播放列表正好对应频道自己的栏目划分（期权的重要思想 / 交易心理重塑和市场理解 / 使用定量处理线性市场 …），直接用播放列表名作标签，按收录关系分配，一个视频可属多个标签。9 个视频同时在 3 个播放列表里。未被收录的 91 个视频归入「未归类」。

**2. 引用：必须按「区块语义」判断，不能按「有链接」判断。**
简介里的链接分成三种性质，混在一起处理会出错：

- `✳️ 其他期权视频：` / `其他定量视频：` —— 逐期复制的模板清单（出现 165 / 8 次），**不是引用，剔除**；
- `✏️ 视频中推荐的本频道其他资料和视频（按出现顺序排列）：` —— 作者主动列出的引用，**保留**；
- `系列视频链接👇：` / `相关视频链接：` —— 作者列的系列清单，**保留**。

清洗后得到 **34 条真实简介引用**。除此之外，字幕不可得，正文里也没有「上一期/承接前文」这类可解析的交叉指代（全频道只有 1 处），因此这一条只留下 1 条待人工确认的记录——这是数据事实，不是筛选阈值的问题。

**3. 系列结构是另一条可验证的线索。**
标题里存在明确的系列标记：`（第一集…第八集）`、`[上]/[下]`、`Day 1–5`、`XX系列 - `。同一系列内按集数/日期串联，得到 **25 条系列关联**。这类关系在页面上用**虚线 + 紫色**区分，不冒充「明确引用」。

> 最终：**59 条关联**（34 条简介引用 + 25 条系列关联），1 条待确认。没有为了凑数把模板清单算成引用。

## 二、目录结构

```
PUG_VideoMap/
├── index.html            # 交付物（构建产物，含内联数据，可直接双击打开）
├── data/
│   ├── manual.json       # 人工维护覆盖层（唯一需要手改的文件）
│   └── index.json        # 构建出的结构化数据（检查/复用）
├── tools/
│   ├── collect.py        # 采集：视频列表 / 播放列表 / 逐条元数据（带缓存）
│   ├── build.py          # 清洗 + 归并 + 打包成 index.html
│   └── refresh.sh        # 一键更新
├── web/                  # 页面源码（模板 / 样式 / 逻辑），改完需重新 build
└── raw/                  # 原始抓取缓存（可删，重跑会重建）
    ├── collected.json
    ├── videos/<videoId>.json
    └── playlists/<playlistId>.json
```

## 三、更新流程

```bash
./tools/refresh.sh          # = collect.py + build.py
```

首次采集约 3–5 分钟（380 个视频页，6 并发）；之后有缓存，只抓新增视频，通常几十秒。

`collect.py` 只负责取数，`build.py` 负责清洗与合并，两者都幂等。频道后续新增视频时：新视频自动进入列表、拿到日期、按播放列表分配标签、按标题规则并入既有系列，**`manual.json` 里的人工修订按视频 ID 保留，不受影响**。

## 四、人工维护：`data/manual.json`

以 YouTube 视频 ID 为索引，全部字段可选，缺省即「不覆盖」：

```jsonc
{
  "tags": {
    "pZRmCv-kfmc": {
      "add": ["PLFzeuKbRQ3c1Scw3lQv8Einmv2L_H-yJR"],   // 加标签（可用播放列表 ID，也可用自定义标签 ID）
      "remove": ["unfiled"]                             // 去掉自动分配的标签
    }
  },
  "refs": {
    "pZRmCv-kfmc": {
      "add": [{ "to": "CC0dUapaBLU", "type": "mention", "note": "开场提到上一期" }],
      "remove": ["agJUm5hxZLs"]                        // 删掉自动推断的关联
    }
  },
  "tagDefs": [
    { "id": "theme-0dte", "label": "0DTE 专题", "color": "#e0895b" }
  ],
  "pendingDismissed": ["oXjxx5jH2gw"]                  // 已审阅、无需处理的待确认项
}
```

- `type`: `mention`（明确引用，实线蓝）或 `series`（系列关联，虚线紫）。
- 自动与人工的合并规则：**自动结果 ∪ add − remove**；同一目标同时存在两类来源时，以 `mention` 为准。
- 规则在 `web/app.js` 的 `mergeTags / mergeRefs` 与 `tools/build.py` 中保持一致；页面运行时也用同一套规则合并，所以网页上的改动与文件改动效果完全相同。

### 在网页上改，再固化回文件

1. 点右上角「维护」→ 点任意行右侧的「编辑」；
2. 勾选/取消标签、`×` 删除引用、输入标题搜索并新增引用；
3. 改动实时生效并暂存在浏览器 `localStorage`（右上出现「导出修订 (n)」）；
4. 点「导出修订」下载 `manual.json`，覆盖 `data/manual.json`，再跑一次 `./tools/refresh.sh` 即固化；
5. 「重置」丢弃本地暂存，回到文件版本。

## 五、页面交互

- **列表**：380 行，按发布日期从新到旧；列为 `发布日期 / 视频名称 / 引用`。点击标题在新标签页打开原视频。左侧 3px 色条是标签染色（多个标签则是分段渐变），悬停可见标签名。
- **筛选**：顶部「全部」+ 15 个播放列表标签 + 自定义标签 + 「未归类」。可多选，取**并集**；「全部」恢复。支持标题搜索，搜索与标签叠加生效。页面长度跟着筛选结果走（380 行约 13 000px、103 行约 4 000px、3 行约 700px），不会留下一条长长的空白滚动区。
- **引用标记**：一行只有**一个**小圆点，与这一行引用了几条无关——有引用才出现。悬停可见它指向哪些视频（多个时列出前 4 个与总数）。同系列内部互相提到的视频不再单独出点，交给下面的方框表达，避免六期互引变成六条重复连线。
- **连线**：点圆点 → 一次性高亮该行引用的**全部**目标，并在右侧留白处为每个目标画一条带箭头的贝塞尔曲线；再次点击取消。可以同时展开多行，曲线并存。`Esc` 清空全部。
- **系列关联**：同一系列的连续几期用**圆角方框**圈在一起，方框不做点击交互，悬停显示系列名与期数。若同系列的两期之间夹了别的视频（例如上下集之间插了一条无关更新），方框会分成两段，并在右侧用一条紫色虚线把它们串起来；筛选把成员打散时同样处理。
- **临时展开**：若某个目标行被当前筛选隐藏，点圆点时强制显示该行并标「临时」；取消后自动收回，筛选状态不变。
- **待确认**：右上「待确认」打开审阅面板。面板顶部解释了这一栏的含义——简介正文里出现「承接之前的内容」「上一期讲过」这类说法，能确定它「提到了本频道的某个视频」却无法确定是哪一期，系统不猜，集中列出来等人工判断；每条给出命中原句，可一键关联到同系列候选、跳转定位或标记忽略。

## 六、已知限制

- **字幕不可得**，所以「视频里口头提到某期」无法自动识别。若日后拿到文字稿（如自行导出），可在 `tools/` 里加一个解析器，产出与 `extract_description_refs` 相同结构即可并入，页面无需改动。
- 系列顺序：有集数/上下集的按编号；`XX系列 - ` 这类无编号的按发布日期串联，顺序为推断值。
- 发布日期取 YouTube 返回的 `publishDate`（美西时区），与频道页面显示一致；极端情况（太平洋时间深夜上传）与本地日期可能差一天。
- 播放列表归属是抓取当时的快照；频道调整播放列表后需重跑 `collect.py`。

## 七、发布到 GitHub Pages

页面已经托管在 GitHub Pages 上，仓库既是成品也是源码：

- 线上地址：`https://<你的 GitHub 账号>.github.io/powerupgammas-index/`
- 仓库地址：本仓库（`<你的 GitHub 账号>/powerupgammas-index`）
- Pages 配置：`main` 分支 / 根目录；仓库根目录的 `.nojekyll` 让 Pages 直接当静态文件伺服，不做 Jekyll 处理
- 仓库是 **public**：GitHub Pages 对私有仓库需要付费计划，本项目内容都是公开视频信息，公开仓库即可

### 日常更新

```bash
./tools/deploy.sh             # 改完页面/数据后：重新构建 + 提交 + 推送
./tools/deploy.sh --refresh   # 频道有新视频时：先重抓数据，再构建推送
```

推送后 Pages 会在 30 秒左右自动重建，分享链接不变。等价的手动步骤：

```bash
python3 tools/build.py
git add -A && git commit -m "update" && git push origin main
```

### 说明

- `raw/`（抓取缓存，约 3MB）和 `.workbuddy/`（本地工作记忆）已在 `.gitignore` 中排除，不会进仓库；换台机器 clone 下来跑一次 `collect.py` 即可重建缓存。
- 只想要成品：仓库根目录的 `index.html` 就是全部，拷走这一个文件放任何静态托管都能用。
